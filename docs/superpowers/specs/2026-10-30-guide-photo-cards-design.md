# 가이드 '핵심 성분' 실사 카드 — 설계 (2026-10-30)

## 의도와 이유
사용자가 커뮤니티에서 본 "전립선 청소약" 이미지(검은 배경, 금색 번호·제목, 성분마다 실사 음식 사진)처럼 **가이드 페이지의 '핵심 성분' 구역**이 보이길 원한다. 지금 구역은 흰 카드 + 라인 아이콘이라 정보는 충분하지만 눈길을 끌지 못한다. 사진이 있으면 "이 성분이 어디서 오는지"가 한눈에 보이고 페이지가 믿음직해 보인다. 브레인스토밍에서 세 시안(다크 프리미엄 / 사이트 톤 + 실사 / 매거진형) 가운데 **A안 다크 프리미엄**을 골랐다.

## 목표
- 가이드 90편 모두의 `#ingredients` 구역을 A안 카드로 바꾼다: 어두운 띠 안에 2열(모바일 1열) 카드, 카드마다 금색 번호(01, 02…)·성분명·금색 한 줄 키워드·흰 설명·복용 메모·오른쪽 아래 실사 사진.
- 성분 87종 각각 **같은 결의 실사 사진** 한 장: 어두운 슬레이트 돌판, 따뜻한 스튜디오 조명, 대표 급원 식재료 + 보충제 알약 몇 개, 글자 없음. ChatGPT(사용자 계정, 크롬)에서 생성한 자체 이미지.
- 사진이 아직 없는 성분은 **공통 기본 사진**(돌판 위 여러 알약)으로 보여 사이트가 깨지지 않는다. 사진은 20장씩 나눠 채워도 된다.
- 기존 정보(성분명 링크, 식약처 인정 기능성, 가이드별 설명 `why`, 복용 시간·하루 섭취량, 성분 페이지 링크)는 그대로 유지한다.

## 비목표
- 성분 사전 페이지·기능성 허브·홈·비교 글은 이번에 바꾸지 않는다(사진 자산은 재사용할 수 있게 성분 id 로 저장).
- 사이트 전체 다크 테마 아님. 어두운 띠는 이 구역에만.
- 앱 전용 처리 없음(앱은 같은 페이지를 열므로 자동 적용).

## 반목표 (이렇게 되면 실패)
- 예시 이미지의 과장 표현("비대 완화", "염증 완화", "세포 손상 방지", "발기력")이 들어가는 것. 금색 한 줄과 본문은 **식약처 인정 기능성 범위**의 기존 데이터(`tags`, `mfdsFunction`, `why`)에서만 나온다.
- 사진에 글자·브랜드·제품 로고·사람 얼굴이 들어가는 것. 생성 프롬프트에 "no text, no letters, no watermark" 를 두고, 변환 전에 눈으로 한 번 확인한다.
- 페이지 무게가 급증하는 것: 사진은 640×640 WebP(품질 80, 약 50KB), `loading="lazy"`, `width/height` 명시. 가이드 한 편의 사진 합계는 보통 300~500KB.
- 대비 부족: 어두운 카드 위 본문은 밝은 크림색(#e9e4d6 이상)으로 WCAG AA 를 지킨다.

## 제약
- 정적 빌드(`scripts/build_site.py` `render_guide`)가 HTML 을 만든다. 스타일은 `assets/css/style.css` 의 커스텀 클래스(`.pc-*`)로 쓰고 새 Tailwind 유틸리티 클래스는 되도록 쓰지 않는다(Tailwind 재생성 범위를 줄이기 위해).
- 원본 PNG(장당 약 2MB, 1254×1254)는 저장소에 넣지 않는다. 저장소에는 변환된 WebP 만 넣는다.
- 사진 제작은 사용자의 ChatGPT 계정을 사용자의 크롬에서 보조 에이전트가 조작해 만들며, 로그인·결제·캡차 같은 일은 하지 않는다. 생성 제한이 걸리면 멈추고 다음에 이어서 한다.

## 결정된 방식
### 데이터·자산
- `data/ingredient-photos.json`(수동): `template`(프롬프트 틀, `{SUBJECT}` 자리) + `default`(공통 기본 사진의 subject) + `items[]`: `{ id, subject, claim }`. `subject` 는 그 성분의 대표 급원(예: 오메가3 = 연어 한 토막 + 호박색 소프트젤). 87종 전부 미리 적어 두고, 생성은 가이드 등장 횟수가 많은 순서로 한다(비타민 D, 오메가3, 마그네슘, 아연, 유산균, 칼슘, 철분, B군, 비타민 C, B12, 엽산 …).
- 사진 파일: `assets/images/ingredients/<id>.webp` (640×640, q80) + `assets/images/ingredients/_default.webp`(공통 기본 사진 — 돌판 위 여러 색 알약, 한 번만 생성).
- 변환: `scripts/convert_photos.py <원본 폴더>` — 폴더의 `<id>.png` 를 읽어 정사각형 확인(아니면 중앙 크롭) → 640 리사이즈 → WebP 저장, 결과 표를 출력. id 가 `data/ingredients.json` 에 없으면 거부.
- 원본 보관: `C:\Users\OK\Pictures\영양제kr-성분사진-원본\<id>.png` (사용자 PC, 저장소 밖). 이 PC 가 아니어도 WebP 는 저장소에 있으니 사이트는 문제없다.
- 빌드 `validate_photos`: `ingredient-photos.json` 의 id 가 성분 사전에 있는지, 성분 사전의 모든 id 가 표에 있는지(빠지면 경고가 아니라 실패) 검사. 사진 파일 유무는 빌드가 `assets/images/ingredients/` 를 보고 결정한다(있으면 그 사진, 없으면 `_default.webp`).

### 카드 렌더링 (`render_guide`)
- 구역 틀: `<section id="ingredients">` 와 제목·안내문은 그대로. 카드 묶음을 `<div class="pc-band"><div class="pc-grid">…</div></div>` 로 감싼다.
- 카드 하나 `<article class="pc-card">`:
  - `<img class="pc-photo" src="../assets/images/ingredients/<id|_default>.webp?v=…" alt="" width="640" height="640" loading="lazy" decoding="async">` — 장식용이라 alt 는 빈 문자열(성분명은 텍스트로 있음). `?v=` 해시는 기존 자산 스탬프 규칙을 따르되 이미지는 내용 해시가 없어도 되므로 파일 경로만 써도 된다(빌더 판단).
  - 머리: `<span class="pc-num">01</span>` (가이드의 성분 순서) + `<a class="pc-name" href="../i/<id>.html">성분명</a>`
  - 금색 한 줄 `<p class="pc-claim">`: `data/ingredient-photos.json` 의 성분별 `claim`(14자 안팎, 수동). `tags` 를 그대로 쓰지 않는 이유: 태그에는 '골다공증·빈혈·항염·구내염' 같은 질병·효능 어휘가 있어 카드의 가장 눈에 띄는 자리에 두면 표현 원칙과 부딪힌다. `claim` 은 `mfdsFunction` 의 인정 표현을 짧게 줄인 말만 쓴다(예: 오메가3 "혈행 · 중성지질", 칼슘 "뼈 · 치아 형성", 철분 "산소 운반 · 혈액 생성"). 빌드 `validate_photos` 가 `claim` 을 금칙어 목록(치료·예방·완치·진단·완화·항염·빈혈·구내염·비대·질병명)으로 검사하고, 빠진 성분은 실패.
  - 본문 `<p class="pc-desc">`: 기존 `why`(용어 자동 링크 `term_html` 유지).
  - 메모 `<p class="pc-meta">`: 기존 "복용 시간 · 하루 섭취량".
  - 기존 식약처 문구 줄(`mfdsFunction` 70자)은 카드에서 빼지 않고 `pc-claim` 아래 작은 회색 줄로 유지한다(인정 범위를 보여 주는 근거).
- 쇼핑·비교 등 다른 구역은 손대지 않는다.

### 스타일 (`style.css`)
- `.pc-band`: 배경 `radial-gradient(120% 80% at 50% 0%, #1b1b1b, #0b0b0b)`, 둥근 모서리 20px, 안쪽 여백 18~22px, 흰 글자.
- `.pc-grid`: `grid-template-columns: repeat(2, 1fr)`, 간격 12px; 768px 미만에서 1열.
- `.pc-card`: 상대 위치, 배경 #141414, 테두리 #3a3a3a, 둥근 14px, 최소 높이 190px, 그림자. `.pc-photo` 는 절대 위치로 오른쪽 아래 60% 너비·72% 높이, `object-fit: cover`, 왼쪽 위로 사라지는 마스크(`mask-image: linear-gradient(135deg, transparent 0%, #000 45%)`), 모바일은 너비 52%.
- `.pc-num`: 금색 그라데이션 원(#ffe39a → #d9a62a), 진갈색 숫자. `.pc-claim`: 금색(#ffd466) 굵게. `.pc-desc`: #e9e4d6, 본문 너비는 사진을 피하도록 `max-width: 58%`. `.pc-meta`: #9a9483.
- 링크 호버: 성분명 밑줄. 인쇄(`@media print`)에서는 띠 배경을 흰색으로, 사진은 숨긴다.

### 사진 제작 파이프라인
- 보조 에이전트(작은 컨텍스트, 스크린샷 없음)가 크롬의 ChatGPT 에 `template`+`subject` 프롬프트를 넣고, 생성된 이미지를 JS 로 내려받아(`yj-<id>.png`) 원본 폴더로 옮긴다. 한 번에 10~20장, 장당 40~60초.
- 각 묶음이 끝나면 `convert_photos.py` 로 변환 → 변환본을 눈으로 훑어(글자·이상한 물체) 문제 있는 것만 다시 생성 → 빌드 → 커밋·푸시.
- 첫 10장으로 사용량(5시간 한도 %)을 재서 사용자에게 알리고 계속 여부를 정한다.

### 테스트
- Python: `validate_photos` 가 모르는 id·빠진 id 를 거부하고 실제 파일을 통과시킨다. `render_guide` 가 사진 파일이 있으면 `<id>.webp`, 없으면 `_default.webp` 를 쓴다. 카드 문구에 금칙어(치료·예방·완치·진단·비대 완화·염증 완화)가 없다(가이드 전편 빌드 결과 검사). `convert_photos.py` 가 작은 가짜 PNG 를 640 WebP 로 바꾸고 모르는 id 를 거부한다.
- 브라우저: 데스크톱·모바일(540px)에서 가이드 한 편 확인(사진 위치, 글이 사진을 가리지 않는지, 기본 사진 대체).

## 빌더 점검에서 정한 것 (작성자 결정)
- **배포 순서**: 카드 코드는 `_default.webp` 가 저장소에 있어야 `check_site` 를 통과한다. 기본 사진은 첫 생성 묶음의 첫 장으로 ChatGPT 에서 만든다(`default.subject`). 생성이 막힌 상황이면 임시로 `assets/images/home/hand-softgel.webp` 를 640×640 으로 중앙 크롭해 `_default.webp` 로 두고 코드를 먼저 배포해도 된다(그 단계에서 90편이 같은 기본 사진으로 보이는 것은 허용). 진짜 사진이 생기면 교체.
- **금색 한 줄**: 위 `claim` 필드로 확정(태그 사용 안 함).
- **사용자 참여**: 내려받기는 묶음(10~20장) 단위로 채팅에서 한 번 승인받고 보조 에이전트가 무인으로 진행한다(장당 승인 아님). 검수는 Claude 가 변환본을 이미지로 읽어 글자·이상한 물체를 거르고, 묶음마다 사용자에게 축소 모음 한 장을 보내 눈으로 훑게 한다. 사용량은 ChatGPT 가 아니라 Claude 쪽 5시간 한도 % 를 묶음 전후로 재서 보고하고, ChatGPT 쪽은 제한 메시지 발생 여부·장수·소요 시간으로 기록한다.
- **구현 메모**: 이미지 `?v=` 는 `render_guide` 에서 파일 내용 해시(`asset_digest`)로 직접 붙인다(서비스워커가 `/assets/` 의 `?v=` 주소를 cacheFirst 로 두므로 교체 시 캐시 갱신 보장). `build_site.py` 는 Pillow 없이 파일 유무만 보고, Pillow 는 `convert_photos.py` 만 쓴다(CI 빌드 의존성 유지). 사진 존재 여부는 `prepare_*` 패턴으로 `core["photos"]` 에 담아 `render_guide` 를 순수하게 두어 테스트하기 쉽게 한다.

## 빌더에게 맡기는 것
- CSS 세부 값(그림자·여백·글자 크기)과 호버 효과.
- 사진이 글과 겹치는 좁은 화면에서 본문 `max-width` 조정.
- `?v=` 스탬프를 이미지에도 적용할지(적용하면 사진 교체 때 캐시가 바로 갱신됨) — 기본은 적용.
- 공통 기본 사진 `_default.webp` 의 프롬프트.
