# 영양제.kr 모바일 앱(복용 알림) 설계

작성 2026-10-20. 사용자와의 브레인스토밍 결과를 정리한 설계 문서. 구현 계획은 이 문서를 바탕으로 따로 세운다.

## 1. 의도와 이유

영양제.kr 사이트를 구글 플레이와 애플 앱스토어에 올린다. 사이트는 성분 사전·궁합 체크·복용 시간표·가이드를 제공하는 정적 사이트이고, 앱은 같은 화면을 그대로 쓰되 **복용 시간 알림**이라는 앱에서만 가능한 기능을 더한다. 사용자가 아침에 영양제를 챙기는 순간 휴대폰이 "아침 식후 영양제 시간이에요 — 비타민 D · 오메가3" 하고 알려 주는 것이 핵심 장면이다.

왜 지금인가: 사이트 콘텐츠(성분 81종·궁합 710쌍·가이드 87편)와 궁합·시간표 로직이 갖춰져 앱이 보여 줄 내용은 이미 있다. 남은 것은 포장과 알림이다. 애플 심사는 웹사이트를 그대로 감싼 앱을 "최소 기능" 미달로 거절하는 일이 흔하므로, 알림·기록처럼 앱다운 기능이 있어야 통과 가능성이 생긴다.

## 2. 목표 · 비목표 · 안티골

**목표**
- 앱 하나를 만들어 두 스토어에 낸다. 안드로이드 먼저, iOS 는 그 뒤.
- 회원가입 없이 쓴다. 내 영양제·알림 설정·복용 기록은 휴대폰 안에만 저장한다.
- 사이트 내용을 고치면 앱도 같은 내용을 보여 준다(앱 재심사 없이).
- 사이트 방문자에게도 이득이 있어야 한다: PWA 설치, 내 영양제·시간표는 웹에서도 동작(알림만 앱 전용).

**비목표(이번에 하지 않음)**
- 회원가입·로그인·서버 동기화·서버 푸시. 필요해지면 별도 프로젝트.
- 의약품(처방약·일반약) 복용 관리. 내 영양제에는 영양제 성분만 넣는다(아래 7절의 제 결정).
- 위젯, Apple Watch, 구매·재고 알림, 커뮤니티.
- 앱 전용 디자인. 앱은 사이트 화면을 그대로 쓴다.

**안티골(이렇게 되면 실패)**
- 사이트가 느려지거나 런타임 CDN·프레임워크가 들어오는 것(CLAUDE.md 규칙 위반).
- 코드베이스가 둘로 갈라져 사이트와 앱을 따로 고쳐야 하는 상태.
- 개인정보 수집이 늘어나는 것. 지금은 GA4 방문 통계뿐이며 그 수준을 유지한다.
- 건강 정보 표현이 식약처 기능성 범위를 벗어나는 것(알림 문구 포함).

## 3. 제약

- 스택: 정적 HTML + Tailwind 정적 빌드 + Vanilla JS. 생성 파일은 `scripts/build_site.py` 가 만든다. 1st-party 스크립트는 `defer`. 자산 링크에는 빌드가 `?v=해시` 를 붙인다.
- 개발 환경: 윈도우 PC, Mac 없음, 아이폰·아이패드 있음. iOS 빌드는 GitHub Actions macOS 러너(공개 저장소라 무료)로 한다. 안드로이드 폰도 있다(사용자 확인): 안드로이드 앱은 PC 에서 빌드하거나 GitHub Actions 산출물(APK)을 받아 본인 폰에 설치해 알림까지 확인한다.
- 구글 플레이 비공개 테스트에 필요한 테스터(12명 이상·14일)는 충분히 있다(사용자 확인).
- 저장소는 공개로 유지한다(제 추천, 6절). 서명 키·API 키는 GitHub Secrets 에만 둔다.
- 배포: Cloudflare Pages 가 기본 브랜치를 push 마다 배포. `_headers` 가 JS/CSS 를 1년 불변 캐시, `data/*` 를 5분 캐시한다.
- 1인 운영. 스토어 계정·심사 대응·스크린샷 촬영은 사용자가 한다.

## 4. 전체 구조 (제 결정)

```
[영양제.kr 사이트]  ── 그대로 ──▶  [PWA]  ── Capacitor 로 감싸기 ──▶  [안드로이드 앱] [iOS 앱]
  내 영양제·시간표·기록(웹 코드)                                        알림 예약만 네이티브
```

1. **사이트를 PWA 로**: `manifest.webmanifest`, 아이콘 세트, 서비스워커(오프라인 폴백 + 자산 캐시), iOS 용 `apple-touch-icon`·메타. 스토어 없이도 홈 화면 설치가 되고, 앱의 오프라인 동작도 이 서비스워커가 맡는다.
2. **Capacitor 가 라이브 사이트를 연다**: 앱은 번들 대신 `https://xn--og5b1hx9c.kr` 를 웹뷰로 연다(`server.url`). 그래서 사이트를 고치면 앱도 바로 같은 내용이고, 앱의 origin 이 사이트와 같아 `localStorage`·GA4·링크가 사이트와 똑같이 동작한다. Capacitor 는 이 origin 에 네이티브 브리지를 주입하므로 사이트 JS 가 `window.Capacitor` 를 보고 "앱 안"임을 안다.
3. **기능은 웹 코드에, 알림만 네이티브에**: 내 영양제·시간표·기록·내보내기는 사이트 JS(`assets/js/`)로 만든다. 알림 예약은 앱 안에서만 Capacitor Local Notifications 플러그인으로 하고, 웹에서는 같은 자리에 "앱에서 알림 받기" 안내를 보여 준다.
4. **안드로이드도 Capacitor**: TWA 대신 Capacitor 를 써서 두 플랫폼의 포장·플러그인을 하나로 맞춘다.
5. **앱에서는 쇼핑 버튼을 숨긴다(1차 출시, 사용자 결정)**: `affiliate.js` 가 앱 안임을 감지하면 쿠팡·링크프라이스 등 구매 버튼과 제휴 고지를 그리지 않는다. 제품 찾기·제품 상세의 정보(성분·신고 내용)는 그대로 보여 준다. 쿠팡 파트너스 최종승인 뒤 앱을 채널로 등록하고 `config.js` 의 플래그 하나로 켠다.

왜 라이브 사이트 방식인가: 번들 방식이면 성분·가이드를 고칠 때마다 앱을 다시 심사받아야 하고, 성분 페이지(`i/*.html`)가 생성 파일이라 앱 안의 사본이 금방 낡는다. 위험은 애플이 "원격 웹 래핑"으로 볼 수 있다는 점인데, 알림·기록·내 영양제가 있으면 기능으로 방어한다. 심사에서 그래도 거절되면 그때 번들 방식(사이트 빌드 결과를 앱에 복사)으로 바꿀 수 있도록 사이트 JS 는 origin 에 의존하지 않게 짠다.

## 5. 기능 설계

### 5-1. 내 영양제 (웹·앱 공통)

- 새 페이지 `my.html`(noindex). 섹션: 먹고 있는 영양제 목록 → 오늘 시간표 → 복용 기록(켠 경우) → 알림 설정(앱) → 내보내기·가져오기.
- 추가 경로: ① `my.html` 의 검색창(성분 자동완성, 기존 `Data.search` 재사용) ② 궁합 체크 결과의 "내 영양제로 저장" 버튼(선택한 성분 전체) ③ 성분 페이지의 "내 영양제에 추가" 버튼.
- 항목은 성분 id 와, 사용자가 바꾼 경우에만 시간대를 저장한다. 이름·기본 시간대·주의 문구는 `ingredients.json` 에서 매번 읽으므로 데이터가 갱신되면 앱도 따라간다.
- 시간표는 `schedule.js` 의 `Schedule.build` 를 그대로 호출한다(궁합 간격 규칙으로 시간대 이동까지 동일). 시간대 이름도 사이트와 같다: 아침 공복 · 아침 식후 · 식전 · 점심 식후 · 저녁 식후 · 취침 전.
- 시간대 직접 바꾸기(제 결정): 목록의 성분마다 시간대를 바꿀 수 있다. 바꾼 성분은 시간표와 알림이 그 시간대를 따르고, 궁합 간격 규칙과 어긋나면 "칼슘과 2시간 간격을 권해요" 같은 메모로만 알린다. 마그네슘을 아침에, 유산균을 저녁에 먹는 사용자가 흔하기 때문이며, 출시 뒤에 넣으면 저장 형식을 바꿔야 해서 처음부터 넣는다.
- 진입점(제 결정): 헤더 메뉴와 홈에 "내 영양제" 를 추가하고, 웹의 모바일 탭 바는 지금 5개(홈·성분·궁합·가이드·제품)를 유지한다. 앱 안에서만 홈 탭을 "내 영양제" 로 바꿔 첫 화면처럼 쓴다.

### 5-2. 알림 (앱 전용)

- 설정: "복용 알림 받기" 전체 토글, 시간대별 알림 시각과 개별 토글(시간표에 영양제가 있는 시간대만 표시), "알림에 성분 이름 표시", "주말에도 알림".
- 기본 시각(제 결정): 아침 공복 07:30 · 아침 식후 08:00 · 식전 11:30 · 점심 식후 12:30 · 저녁 식후 19:00 · 취침 전 22:30. 사용자가 시각을 누르면 시계로 바꾼다.
- 문구: 제목 "아침 식후 영양제 시간이에요", 본문 "비타민 D · 오메가3" + 해당 시간대의 한 줄 팁(성분의 `timing.note` 중 첫 항목 또는 시간대 설명). 기능성·효능 표현은 넣지 않는다.
- 동작 버튼: "먹었어요"(기록이 켜진 경우만 표시), "30분 뒤 다시". 알림을 누르면 `my.html` 의 오늘 시간표로 연다.
- 재예약: 내 영양제·시각·토글이 바뀔 때마다 기존 예약을 모두 취소하고 다시 건다. 매일 반복 예약이며 서버는 없다.
- 권한: 처음 알림을 켤 때 OS 권한을 묻고, 거부되면 설정 화면으로 안내하는 문구를 보여 준다.
- 웹(PWA)에서는 이 섹션 자리에 "휴대폰 알림은 앱에서 받을 수 있어요" 안내와 스토어 링크(출시 뒤)를 보여 준다.

### 5-3. 복용 기록 (사용자가 켜고 끄는 선택 기능)

사용자 결정: A(알림만)·B('먹었어요' 체크)·C(체크 + 주간 기록)를 모두 만들되 사용자가 골라 쓰게 한다.

- 설정 "복용 기록 남기기" 토글 하나로 B·C 가 함께 켜진다. 꺼져 있으면 A 처럼 알림과 시간표만 보인다.
- 처음 내 영양제를 저장할 때 "복용 기록도 남길까요?" 를 한 번 묻고(기본 선택 '네'), 이후는 설정에서 바꾼다(제 결정).
- 켜면: 오늘 시간표의 시간대마다 체크 버튼, 상단에 "오늘 3개 중 2개" 와 연속 일수, 알림의 "먹었어요" 버튼이 같은 체크를 기록한다.
- 기록 보기: 최근 7일 줄 보기와 30일 달력. 날짜를 누르면 그날 시간대별로 무엇을 챙겼고 빠뜨렸는지 보여 준다.
- 기록은 날짜·시간대·체크 여부만 저장한다(휴대폰 안). 끄면 새 기록을 남기지 않고, 기존 기록은 "기록 지우기" 로 사용자가 지운다.

### 5-4. 내보내기 · 가져오기 (회원가입 대체)

- 내보내기: 내 영양제 목록(바꾼 시간대 포함)과 알림 설정을 담은 링크(`my.html#import=…` — 해시 조각에 실어 서버·방문 통계·서비스워커 캐시 키에 남지 않게)와 그 링크의 QR 코드, 그리고 붙여넣기용 짧은 텍스트 코드. 기록(5-3)은 포함하지 않는다.
- 가져오기: 링크를 열면 "이 목록을 가져올까요?" 확인 뒤 저장(기존 목록과 합치기/바꾸기 선택). 앱에서는 텍스트 코드 붙여넣기도 받는다.
- 아이폰 ↔ 아이패드, 웹 ↔ 앱 이동이 목적이다. 앱이 링크를 직접 받는 유니버설 링크·앱 링크 설정은 2차 과제로 두고, 1차에서는 링크가 웹을 열고 텍스트 코드로 앱에 넣는 흐름까지 만든다.
- QR 생성은 런타임 CDN 없이 저장소에 둔 작은 라이브러리나 자체 구현으로 한다.

### 5-5. 저장

- 저장소 모듈 하나(`assets/js/store.js`, 가칭)가 내 영양제·설정·기록을 읽고 쓴다. 웹은 `localStorage`, 앱에서는 같은 `localStorage` 에 더해 Capacitor Preferences 에 복제해 OS 백업(iCloud·구글)에 실리게 한다.
- 스키마에 버전 번호를 둔다. 성분 id 가 데이터에서 사라지면 목록에서 조용히 제외하고 한 번 알린다.

## 7. 결정 사항 정리

**사용자가 정한 것**
- 앱으로 만들어 두 스토어에 낸다. Mac 없이 아이폰·아이패드로 테스트한다.
- 앱 전용 기능은 복용 시간 알림이다.
- 회원가입 없이 "기기 안 저장 + 링크·QR 로 옮기기".
- 알림 뒤 기능은 A·B·C 모두 만들고 사용자가 선택해 쓴다.
- 플레이 비공개 테스트 테스터는 충분하다. 안드로이드 먼저 가는 순서를 유지한다.
- 1차 출시 앱에서는 쇼핑 버튼을 숨기고, 쿠팡 파트너스 최종승인 뒤 앱을 채널로 등록하고 켠다.
- 저작권 등록을 신청할 계획이다(시점은 6절).

**제가 정한 것(틀리면 바꿔 주세요)**
- Capacitor 로 라이브 사이트를 여는 구조, 안드로이드도 Capacitor(4절).
- 내 영양제에는 영양제 성분만, 의약품은 제외. 이유: 처방약 복용 관리는 안전 책임이 다르고 사이트도 의약품에는 구매 링크를 두지 않는 등 선을 긋고 있다.
- 기본 알림 시각 6개(5-2), 복용 기록은 첫 저장 때 한 번 묻고 기본 '네'(5-3).
- 성분마다 시간대를 직접 바꿀 수 있게 하고 저장 형식에 처음부터 반영(5-1).
- `my.html` 신설·noindex. 웹 탭 바는 5개 유지, 헤더 메뉴·홈에 진입점, 앱에서만 홈 탭을 내 영양제로(5-1).
- 앱 이름 "영양제.kr", 앱 ID `kr.yeongyangje.app`, 아이콘은 기존 파비콘 기반.
- 개인정보처리방침은 약관과 별도 페이지.
- GA4 는 앱에서도 같은 스트림으로 집계하되 `platform=app` 속성으로 구분.
- 유니버설 링크·앱 링크는 2차.
- 저장소는 공개 유지(6절의 이유).

**승인**: 2026-10-20 사용자가 이 문서대로 진행하는 데 동의함(안드로이드 폰 보유 확인 포함).

## 8. 빌더에게 맡기는 것

- 서비스워커 캐시 전략 세부(정적 자산은 해시 기반 영구, `data/*` 는 네트워크 우선, 오프라인 폴백 페이지)와 `build_site.py` 에서 캐시 목록을 생성하는 방법.
- QR 라이브러리 선택 또는 자체 구현, 내보내기 코드의 인코딩.
- Local Notifications 세부: 주말 제외 스케줄링 방식, 안드로이드 13+ 알림 권한과 정확 알람 권한, iOS 반복 알림 상한(64개) 안에서의 예약 수.
- Capacitor 프로젝트 위치(`app/` 폴더 제안)와 사이트 빌드·`?v=` 해시와의 관계, 앱 안에서 `window.Capacitor` 감지 방식.
- GitHub Actions 의 안드로이드·iOS 빌드 파이프라인, 서명 방식(App Store Connect API 키 + 자동 프로비저닝 등).
- 아이콘·스플래시 생성 파이프라인.
- 저장 스키마와 마이그레이션, 테스트 방법(웹은 로컬 서버와 브라우저, 앱은 실기기).

## 9. 단계

1. PWA 화 + `privacy.html` + 아이콘 세트 — 사이트 배포만으로 효과가 나고 뒤 단계의 전제.
2. 내 영양제·시간표·기록·내보내기(웹 코드) — 웹에서 먼저 완성하고 로컬 브라우저로 검증.
3. Capacitor 안드로이드 + 알림 플러그인 연결 — 실기기(안드로이드 기기 또는 에뮬레이터)로 알림 확인.
4. 구글 플레이 비공개 테스트 → 정식 출시.
5. iOS: GitHub Actions 빌드 → TestFlight(아이폰·아이패드) → 심사 제출.
