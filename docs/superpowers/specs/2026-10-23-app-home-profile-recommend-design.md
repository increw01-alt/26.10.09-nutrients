# 앱 홈·제품 추가·내 정보 맞춤 추천·사용 설명 설계

> 작성일: 2026-10-23 · 상태: 사용자 승인(2026-10-23 "진행", 검토 뒤 결정 사항은 7절) → 계획(writing-plans)
> 배경 설계: `docs/superpowers/specs/2026-10-20-mobile-app-reminders-design.md`(내 영양제·알림·앱)

## 1. 의도

플레이 내부 테스트·TestFlight 로 앱을 써 본 사용자(운영자)의 요청이다. 앱이 '내 영양제' 목록으로 열려서 아침에 켰을 때 "지금 뭘 먹어야 하는지"가 바로 보이지 않고, 제품(센트룸 맨처럼 한 알에 여러 성분)을 넣을 방법이 없으며, 내 상황(연령·성별·고민·생활·약)에 맞는 추천과 구매 연결이 없고, 쓰는 법을 설명하는 페이지가 없다. 또 추천이 "믿을 만한 근거로 골라졌다"는 느낌을 주고 싶어 한다.

브레인스토밍(2026-10-23, 시안 5장)에서 사용자가 정한 것:
- 앱 첫 화면은 **A(오늘 한눈에) + B(타임라인)** 합본. 설치 직후(저장한 영양제 없음)는 시작 안내 3단계.
- 내 정보 항목은 **연령대·성별·고민(여러 개)·생활 상황(여러 개)·복용 중인 약** 다섯 개.
- 추천은 **근거를 보여 주는 맞춤 추천**. 실시간 AI 모델은 붙이지 않는다. 배지 문구는 "AI로 정리한 식약처 인정 기능성 데이터 기반".
- 영양제를 추가한 직후 **아래에서 올라오는 요약 창(A)** 에 궁합 요약과 배정 시간대를 바로 보여 준다.
- 제품은 **한 줄(제품)로** 넣고 시간대는 제품째로 하나, 궁합은 성분 전체로 계산한다.
- 다섯 묶음을 **한 번에** 만든다.

## 2. 목표 · 비목표 · 반목표

목표(이 설계가 끝나면 되는 것):
1. 앱을 열면 '오늘' 홈(`today.html`)이 뜬다. 저장한 영양제가 있으면 인사·다음 복용·오늘 시간표·오늘의 한 줄·바로가기, 없으면 시작 안내.
2. 하단 탭에 홈이 있다(앱: 홈·내 영양제·궁합·가이드·성분).
3. 내 영양제에서 제품명으로 검색해 제품을 한 줄로 추가할 수 있고, 추가 직후 요약 창이 뜬다(성분 추가도 같은 창).
4. 내 정보를 저장하면 '맞춤 추천' 페이지가 근거 칩과 함께 성분을 추천하고, '내 영양제에 추가'·구매 버튼이 붙는다.
5. 사용 설명 페이지가 있다.
6. 모든 새 로직은 순수 함수로 분리해 Node 테스트가 있고, 기존 테스트·빌드·점검이 통과한다.

비목표(이번에 하지 않음):
- 실시간 AI 모델 호출, 서버·계정·동기화. 데이터는 지금처럼 기기 안(localStorage)에만 둔다.
- 제품의 성분별 함량을 읽어 상한을 계산하는 것(함량 데이터가 색인에 없음). 겹침은 "같은 성분이 들어 있다"까지만 알리고 상한은 성분 사전의 `dosage.upper` 문구로 안내한다.
- 안드로이드·iOS 네이티브 코드 변경. 앱 쪽은 `capacitor.config.json` 의 시작 주소만 바뀐다(새 AAB·TestFlight 빌드는 사용자가 조직 계정 재업로드 때 함께).
- 웹 메인(`index.html`)·셀프체크(`finder.html`) 페이지의 구조 변경. 둘 다 그대로 두고 재사용만 한다.

반목표(이렇게 되면 실패):
- "AI가 분석·진단한다"는 표현, 질병 치료·예방·완치 표현, 식약처 인정 범위를 벗어난 효능 문구.
- 건강 고민·복용 약 정보가 서버·분석 도구·주소 쿼리로 나가는 것(내 정보는 저장소와 옮기기 코드에만 담는다).
- 한 제품의 성분이 서로 다른 시간대로 흩어지는 것.
- 기존 사용자의 저장 데이터·옮기기 코드(`YJ1-…`)가 깨지는 것.
- 성분 검색 자동완성·홈 빠른 체크 등 기존 흐름이 느려지거나 깨지는 것(제품 색인은 내 영양제에서 입력할 때만 받는다).

## 3. 제약

- 스택·규칙은 `CLAUDE.md` 그대로: 정적 HTML + Tailwind 정적 빌드 + Vanilla JS, 런타임 CDN 없음, 새 Tailwind 클래스·lucide 아이콘을 쓰면 `npm run assets`, 생성 파일은 빌드가 만들고 `?v=` 스탬프 때문에 JS·CSS 수정 뒤 반드시 `python scripts/build_site.py`.
- 새 정적 페이지(`today.html`·`recommend.html`·`help.html`)는 다른 루트 페이지와 같은 머리(`viewport-fit=cover`, pwa 마커, canonical 확장자 없는 주소)를 갖고, `scripts/build_site.py` 의 정적 페이지 목록·sitemap·sw precache·`check_site.py` 검사 대상에 들어간다. `today.html`·`recommend.html` 은 개인 데이터 화면이므로 `my.html` 과 같은 robots 처리(색인 여부는 `my.html` 을 따른다), `help.html` 은 색인한다.
- 건강 표현: 추천·팁 문장은 성분 사전(`mfdsFunction`·`benefits`·`timing.note`·`dosage`·`whoFor`)과 가이드 색인에 이미 있는 문구만 조합한다. 새로 쓰는 문장(시작 안내·설명 페이지·일반 팁)은 "~에 도움을 줄 수 있음" 범위와 "진단·치료 목적이 아닌 참고 정보" 고지를 지킨다.
- 쿠팡: `config.js` 의 `appShopping` 은 쿠팡 파트너스 최종승인·API 키 뒤에 사용자가 켠다. 그때까지 앱에서는 구매 버튼 자리에 '제품 찾기'(사이트 안 `products.html?ingredient=<성분id>`) 링크를 두고, 켜지면 `Affiliate.buttonsHtml` 로 바뀐다. 쇼핑 버튼이 보이는 화면에는 제휴 고지(`Affiliate.disclosure`)도 함께.
- 알림·시간표의 시간대 상수(`SLOT_ORDER`·`SLOT_META`)는 `store.js`·`schedule.js`·`build_site.py` 가 같아야 한다(기존 테스트가 대조).
- 앱은 라이브 사이트를 여므로 웹 배포만으로 반영된다. 단 시작 주소(`server.url`)와 탭 구성은 앱 빌드에 들어가므로 "다음 빌드부터" 적용되며, 그 전 빌드도 `/my` 로 열려 동작은 해야 한다(홈 탭을 누르면 `today.html` 로 간다).

## 4. 결정한 설계

### 4.1 앱 홈 `today.html` (데이터 페이지 이름 `today`)

**두 상태.**
- 저장한 영양제가 없음: 그림 + "먹는 영양제를 저장해 보세요" + 3단계 안내(① 내 영양제 추가 ② 내 정보 입력 ③ 알림 켜기, 각 단계는 해당 화면으로 가는 링크) + 큰 버튼 '내 영양제 추가하기'(`my.html`, 검색창 포커스) + 오늘의 한 줄(일반 팁) + 바로가기(검색·궁합 체크·셀프체크·사용 설명).
- 저장한 영양제가 있음(위에서 아래로):
  1. 날짜(예: 10월 23일 목요일)와 인사. 인사는 기기 시각 기준 05~11시 "좋은 아침이에요", 11~17시 "좋은 오후예요", 17~22시 "좋은 저녁이에요", 그 밖 "늦은 시간이에요".
  2. **다음 복용 카드**(진녹색): 시간대 라벨·시각·성분(제품) 이름 칩·'먹었어요' 버튼. 다음 복용 = 오늘 시간표(`Schedule.build` 결과의 모든 시간대 — `slotOn`·`weekends` 는 알림에만 관여하고 복용 여부와 무관, 7절 ②) 가운데 오늘 아직 안 먹은 것 중 설정 시각이 지금 이후인 가장 이른 것; 그런 게 없으면 아직 안 먹은 것 중 가장 늦은 것(놓친 것, "지나갔어요" 표시); 전부 먹었으면 카드가 "오늘 다 챙겼어요 🎉" 상태. '먹었어요'는 `my.html` 의 체크와 같은 동작(`Store.markDue` + `toggleDone`)이며, 복용 기록을 아직 켜지 않은 사용자(`logEnabled` 가 `null`/`false`)에게는 버튼 대신 "기록을 켜면 여기서 바로 체크해요 · 켜기"(`my.html#my-log` 로 이동).
  3. **오늘 시간표 카드**: 타임라인. 시간대마다 시각·라벨·이름 요약("비타민 D 외 2"), 먹은 것은 흐리게+✓, 다음 복용은 굵게+'지금'/'다음', 나머지는 보통, 알림을 꺼 둔 시간대(`slotOn` false)는 종 꺼짐 아이콘만 덧붙인다. 제목에 "n / m 완료"(m = 오늘 시간표의 시간대 수, `my.html` 의 기록 통계와 같은 모집단).
  4. **오늘의 한 줄 카드**: 4.2 의 팁 한 문장 + 출처 줄("내 영양제 기준 · 식약처 인정 기능성 자료" 또는 "영양 상식").
  5. **바로가기 4개**: 내 영양제(`my.html`)·궁합 체크(`compatibility.html?items=…` — 따로 먹는 성분 id 를 먼저, 그다음 제품 안 성분 id 순으로 `compat.js` 의 상한 8개까지만 담고, 넘치면 바로가기 부제에 "앞 8개"를 표시; 7절 ③)·맞춤 추천(`recommend.html`)·사용 설명(`help.html`).
- 제품은 성분과 똑같이 이름으로 보인다(알림도 제품명).
- 자정이 지나면 `my.html` 처럼 다시 그린다. 알림 버튼(먹었어요·30분 뒤)은 지금처럼 `app.js` 가 `my.html` 로 보내 처리한다(홈에서는 처리하지 않는다 — 한곳에서만 기록하게).
- **앱을 열 때 하던 일**(저장소가 비면 Preferences 복제본에서 복원, 알림창의 우리 알림 정리, 알림 버튼 종류 등록, `remindersOn` 이면 한 번 동기화)은 `my.js` 에서 `app.js` 로 올려 앱 모드의 모든 페이지에서 한다(7절 ①). `AppBridge.ready()` 는 앱 모드에서 복원이 끝난 뒤 resolve 하고, `today.js`·`my.js` 는 그 뒤에 상태를 읽는다. 동기화는 `window.Reminders`·`window.Schedule`·`window.Store` 가 실린 페이지(`today.html`·`my.html`)에서만 돈다.

**순수 로직 `assets/js/today.js`** (`window.Today` + CommonJS, Node 테스트 `tests/today.test.mjs`): `greeting(date)`, `nextDose(state, sched, now)` → `{ slot, status: "upcoming"|"missed"|"all-done"|"none", time }`, `timeline(state, sched, now)` → 시간대 배열(각 `{ key, label, time, names, done, isNext }`), `tip(items, core, date, generalTips)` → `{ text, source }`.

**앱 설정.** `app/capacitor.config.json` 의 `server.url` 을 `https://xn--og5b1hx9c.kr/today` 로. iOS 는 `server.url` 로 시작하지 않는 주소를 외부로 보지만 `allowNavigation` 에 호스트가 있어 같은 호스트는 앱 안에서 열린다(기존 테스트 `test_in_app_navigation_allowed_for_site_host` 유지, `server.url` 을 검사하는 테스트는 `/today` 로 갱신). `app/www/index.html`(오프라인 안내)의 "내 영양제 열기" 류 문구가 있으면 '홈'으로.

**탭 바(`layout.js renderTabbar`).** 앱: 홈(`today.html`, house)·내 영양제·궁합·가이드·성분. 웹 모바일: 지금 그대로(홈·성분·궁합·가이드·제품). 앱에서 '제품'은 헤더 메뉴에만 남는다. `app.js` 의 "앱에서는 홈 탭이 내 영양제" 주석·로직을 홈=today 로.

### 4.2 오늘의 한 줄

- 사용자의 성분(제품이면 그 안의 성분 포함)에서 문장 후보를 만든다. 후보 원천은 성분 사전의 `timing.note`("{이름}: {timing.label} — {note}"), `dosage.note`, `benefits[0]`("{이름}은(는) {benefit}"), 그리고 궁합 데이터의 시너지 `tip`(사용자 성분끼리의 쌍만). 조사(은/는·을/를)는 `D.josa`.
- 후보가 하나도 없거나 영양제가 없으면 일반 팁. 일반 팁은 `data/tips.json`(수동, 12개 안팎, 각 `{ text, source }`)에 두고 빌드 `validate_tips` 가 금칙어('치료'·'예방'·'완치'·'진단')를 검사한다. 예: "영양제는 '많이'보다 '맞게'. 먹는 것부터 적어 두면 겹치는 성분이 보여요." 같은 생활 문장. 외부 명언은 쓰지 않는다(저작권·출처 문제).
- 날짜별로 결정적으로 고른다: `index = (연도*366 + 일자 순번) % 후보 수` — 같은 날 다시 열어도 같은 문장, 다음 날 바뀐다.

### 4.3 내 영양제: 제품 추가와 '추가 직후 요약 창'

**저장 스키마 v2** (`store.js`, 키는 `yj.my.v1` 유지, `v: 2`, `load()` 가 v1 을 그대로 승격):
- 성분 항목: 지금과 같음 `{ id, addedAt, slot? }`.
- 제품 항목: `{ id: "p:<제품 신고번호>", name: "센트룸 맨", ings: ["vitamin-a", …], addedAt, slot? }`. `ings` 는 추가 시점의 색인 값을 저장한다(색인이 나중에 바뀌어도 사용자의 목록이 흔들리지 않게; `pruneUnknown` 은 제품 안 성분 중 사전에 없는 id 만 조용히 뺀다). 성분이 연결되지 않은 제품은 `ings: []`.
- `profile`(4.4)도 이 상태에 들어간다.
- 옮기기 코드: 접두사 `YJ1-` 유지, 페이로드 `v: 2`. 제품은 `["p:<id>", slot, name]` 만 담는다(성분 목록은 담지 않는다 — QR 한 장 약 2.3KB 한계 때문, 7절 ④). `importCode` 는 v1(성분만)·v2 둘 다 읽고, 가져오는 쪽(`my.js` 가져오기 미리보기)이 제품이 있으면 제품 색인(`D.productNames`, 과거분 포함)에서 `ings` 를 다시 채운다. 색인에 없으면 `ings: []` 로 넣고 "성분 정보를 불러오지 못한 제품은 다시 검색해 추가하면 채워져요" 안내. `merge` 는 제품 id 로 중복을 판단한다. `profile` 은 코드에 포함한다.
- `addItems(state, entries)` 는 성분 id 문자열과 제품 객체(`{ id, name, ings }`)를 함께 받는다.

**검색(`pages/my.js`).** 입력 중 성분(`D.search`, 최대 6) + 제품(`D.productNames` 의 `nameMatcher`, 최대 4; 홈 빠른 체크와 같은 방식, 최근분 먼저·`n.more` 로 과거분) 을 한 목록에 보여 준다. 제품 행은 "제품 · 성분 n가지 · 제조사" 부제. 색인은 내 영양제 검색창에 처음 입력할 때 받는다(페이지 로드 때 받지 않는다).

**시간표(`schedule.js`).** `build(entries, core, overrides)` 의 `entries` 는 성분 id 문자열 또는 제품 객체. 반환 `slots[].items` 는 성분이면 사전 객체, 제품이면 `{ id: "p:…", name, kind: "product", ings: [사전 객체…] }`. `assign` 키는 성분 id 또는 `"p:…"`.
- 제품 기본 시간대: 안에 든 성분들의 `timing.slot` 가운데 가장 많은 것. 동률이면 `morning_after`. 제품 대체 시간대 순서는 `[morning_after, evening_after, lunch_after]` 에서 기본값을 뺀 것.
- 충돌 판정: 제품의 어느 성분이든 상대 항목의 어느 성분과 `separateHours ≥ 1` 이면 두 항목이 충돌. 같은 제품 안의 성분끼리는 충돌로 보지 않는다(한 알에 배합된 것). 제품은 통째로만 옮긴다. 메모 문장에는 제품명을 쓴다.
- `resolvePair` 는 지금처럼 `window.Data` 를 쓰되, Node 테스트를 위해 `build` 가 `opts.resolvePair` 로 주입받을 수 있게 한다(네 번째 인자 `opts`, 없으면 `window.Data.resolvePair`). 테스트 `tests/schedule.test.mjs` 신설.

**알림·기록.** `Reminders.plan` 의 이름 목록은 `opts.shortName(item)` 이 제품이면 `item.name` 을 돌려주도록 `D.shortName` 을 확장한다. 기록·'먹었어요'는 시간대 단위라 바뀌지 않는다.

**추가 직후 요약 창.** `add()` 뒤 `ui.sheet = key` 로 열리는 바텀 시트(`my.html` 안, `role="dialog"`, 배경 누르기·Esc·'확인'으로 닫힘, 열리면 첫 버튼에 포커스).
- 제목: "{이름}을(를) 추가했어요" + 제품이면 "제품 · 한 알에 n가지"(성분 연결이 없으면 "성분 정보 없음").
- 배정 카드: "배정된 시간대 / {라벨} · {HH:MM}" + 이유 한 줄. 이유는 (ⅰ) 시간표 메모에 이 항목이 옮겨진 기록이 있으면 그 문장, (ⅱ) 아니면 성분은 `timing.note` 또는 `timing.label` 기반("{label} 권장"), 제품은 "한 알에 든 성분은 나누지 않고 제품째로 배정해요. {기본 시간대 이유}".
- 궁합 목록: 다른 항목마다 한 줄. 분류는 네 가지 — **겹쳐요**(빨강: 제품 안 성분이 따로 먹는 성분과 같음, 또는 두 제품에 같은 성분; 상세에 `dosage.upper` 가 있으면 "합쳐서 상한({upper}) 안이면 괜찮아요") → **간격 두기·주의**(주황: `caution`/`avoid`, `separateHours` 가 있으면 "n시간 간격 → 시간대를 나눴어요") → **함께 먹으면 좋아요**(초록: `synergy`) → **무난해요**(회색). 항목이 제품이면 성분 쌍 전부를 보고 가장 강한 분류 하나로 요약하고 상세에 어떤 성분 때문인지 적는다. 무난한 항목이 여럿이면 "나머지 n개 — 무난해요" 한 줄로 접는다. 성분 정보가 없는 제품과의 궁합은 "성분 정보 없음".
- 버튼: '시간대 바꾸기'(시트를 닫고 그 항목의 시간대 선택란으로 스크롤·포커스), '확인'.
- 순수 로직 `assets/js/addsummary.js`(`window.AddSummary`, Node 테스트 `tests/addsummary.test.mjs`): `build(core, items, key, sched, opts)` → `{ title, slot, time, reason, pairs: [{ key, name, kind: "dup"|"care"|"good"|"ok", title, detail }], okCount }`. `opts.resolvePair` 주입.

### 4.4 내 정보와 맞춤 추천 `recommend.html`

**내 정보.** 상태 `profile: { age, sex, concerns: [최대 3], life: [], meds: [], updatedAt }`. 선택지는 `data/finder.json` 의 질문을 그대로 쓴다(이미 `type: "multi"`·`max: 3` 이 있고 `Finder.matches`·`parse` 는 배열 답을 처리하므로 엔진 변경은 없다; 내 정보 폼은 그 메타데이터를 그대로 따른다).
- 입력 화면은 `recommend.html` 위쪽의 접이식 폼(처음엔 펼침, 저장하면 칩 요약 + '수정'). 폼 아래에 고지 한 줄: "내 정보는 이 기기에만 저장되고 서버로 보내지 않아요. 다른 기기로 옮기기 코드에는 함께 담겨요."(7절 ⑤). `my.html` 에도 "내 정보 · 맞춤 추천 ›" 한 줄 링크(값이 있으면 칩 요약).
- 저장은 `Store.setProfile(state, profile)`(검증: 질문 id·옵션 값만, 최대 수), 옮기기 코드에 `profile` 포함(v2).
- 어디에도 보내지 않는다: 주소 쿼리·분석 이벤트에 담지 않는다(셀프체크는 쿼리를 쓰지만 추천 페이지는 저장소만 읽는다).

**추천 계산.** `Finder.score(profile + { have: 내 성분 id(제품 안 성분 포함) }, finderData, guidesIndex, core)` 를 그대로 쓴다. 결과 `recommended`(이미 먹는 성분 제외) 상위 8개를 카드로, `have` 가운데 점수 있는 것은 "이미 먹고 있어요"로 흐리게 2개까지, `avoided` 는 "복용 중인 약 때문에 뺀 성분" 문단(셀프체크와 같은 문구), `flags` 는 주의 상자.
- 근거 칩: (ⅰ) **왜**(주황) = 그 성분에 점수를 준 가이드들을 고른 규칙의 `if` 가운데 사용자가 답한 값의 라벨(예: '눈 건강', '40대', '운동 부족'). 같은 라벨은 한 번만, 최대 3개. `Finder.score` 가 `ingredients[].from`(가이드 slug)만 주므로 `Finder.reasons(answers, data, slug들)` 를 더해 "답 라벨" 목록을 돌려준다(순수 함수, 테스트). (ⅱ) **식약처 인정 기능성**(초록) = 성분 사전 `mfdsFunction` 첫 문구(없으면 칩 생략). 카드 본문 한 줄은 그 가이드 색인의 `intro` 가 아니라 성분 사전 `whoFor` 중 사용자 답과 가장 비슷한 것 또는 `summary` 앞 문장(선택은 구현자 재량, 새 문장을 짓지 않는다).
- 버튼: `[data-my-add="<id>"]`(기존 공통 처리) + 구매. 구매는 앱에서 `appShopping` 이 꺼져 있으면 '제품 찾기'(`products.html?ingredient=<id>` — `pages/products.js` 가 읽는 파라미터), 켜져 있거나 웹이면 `Affiliate.buttonsHtml(it.shopQuery)`. 쇼핑 버튼이 보이면 하단에 `Affiliate.disclosure`.
- 머리: 제목 '맞춤 추천', 배지 "AI로 정리한 식약처 인정 기능성 데이터 기반", 설명 한 줄 "식약처 인정 기능성·궁합 자료를 AI와 함께 정리한 데이터베이스에서 내 정보에 맞춰 고릅니다. 진단이나 치료 목적이 아닙니다." 금지 문구: "AI가 분석", "AI 진단", "AI가 당신의 건강 상태를".
- 내 정보가 없으면 폼만 보이고 결과 자리에 "내 정보를 저장하면 추천이 나와요".
- 홈 바로가기 '맞춤 추천' 은 이 페이지로.

### 4.5 사용 설명 `help.html`

정적 페이지 하나(웹·앱 공통, 색인됨). 머리는 다른 내부 페이지와 같은 `.page-hero` 틀, 제목 "영양제.kr 앱 사용 설명", 각 항목은 짧은 설명 2~4문장 + 그 화면의 핵심 요소를 CSS 로 그린 작은 그림(캡처 대신 — 캡처는 스토어용이 나오면 교체 가능). 순서:

8. 다른 기기로 옮기기 — 코드·QR, 내 정보도 함께 옮겨짐

## 7. 검토(빌더 점검) 뒤 정한 것

검토자가 문서만으로 정하기 어렵다고 꼽은 다섯 가지. 모두 만드는 내용이 달라지지 않는 범위에서 작성자가 정했고, 사용자에게 목록으로 알렸다.

① **앱을 열 때 하던 일의 자리** — `my.js` 에 있던 복원·알림창 정리·알림 버튼 등록·열 때 동기화를 `app.js` 로 올린다. 시작 주소가 `/today` 가 되면 `my.html` 을 거치지 않으므로, 재설치한 사용자가 '저장한 영양제 없음' 홈을 보는 일을 막는다. `AppBridge.ready()` 가 복원 뒤 resolve. 테스트는 `tests/app.test.mjs` 확장.
② **`slotOn`·`weekends` 의 뜻** — "알림만 끔(그 시간대도 먹는다)" 으로 둔다. 지금 복용 기록이 그렇게 세고 있어 기존 사용자의 통계·연속 일수가 바뀌지 않는다. 홈 타임라인·다음 복용은 모든 시간대를 보여 주고 알림 꺼짐만 표시한다. (사용자가 "안 먹는 시간대"로 쓰고 싶다면 별도 항목으로 뒤에 검토)
③ **궁합 체크 바로가기와 8개 상한** — `compat.js` 는 건드리지 않고, 따로 먹는 성분 → 제품 안 성분 순으로 8개까지만 넘긴다. 넘치면 바로가기 부제에 "앞 8개". 내 영양제 전체 궁합은 추가 직후 요약 창이 맡는다.
④ **옮기기 코드 크기** — 제품은 `id·name·slot` 만 담고 가져오는 쪽이 제품 색인에서 성분을 다시 채운다. 색인에 없으면 성분 없이 넣고 안내. 저장소의 `ings` 는 추가 시점 값으로 고정되는 원칙은 유지(코드로 옮긴 경우만 가져온 시점 값).
⑤ **민감정보(건강 고민·복용 약) 고지** — 내 정보 폼에 고지 한 줄, `privacy.html` 제5조 갱신을 이번 범위에 넣는다. 스토어 데이터 안전·App Privacy 답안은 전제가 같아 바뀌지 않으나 사용자 재확인 항목으로 기록.

검토자가 확인해 준 사실: `data/finder.json` 은 이미 다중 선택(`type: "multi"`, `max: 3`)이고 `Finder.matches`·`parse` 는 배열 답을 처리한다(4.4 수정). 제품 찾기 주소는 `products.html?ingredient=`. 안드로이드 `assets/capacitor.config.json` 도 sync 산출물로 커밋돼 있어 함께 갱신한다.
